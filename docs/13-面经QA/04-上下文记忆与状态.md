# 04｜上下文、记忆与状态

## Q1：Prompt Engineering 和 Context Engineering 有何不同？

**答：**Prompt Engineering 侧重如何编写指令和示例；Context Engineering 侧重在每一步选择、压缩、隔离和更新哪些信息进入模型窗口。生产系统真正的难点通常不是把 system prompt 写长，而是保证注入的信息新鲜、相关、可追溯且在 token 预算内。

## Q2：短期记忆、长期记忆和任务状态如何划分？

**答：**短期记忆是当前会话的必要上下文，放在窗口或摘要中；长期记忆是跨会话可复用的偏好或事实，需要检索和生命周期治理；任务状态是可恢复的流程数据，如当前步骤、工具结果、审批和 checkpoint，应放在结构化存储中。不要把任务状态混进自然语言历史。

## Q3：长会话如何控制上下文成本与质量？

**答：**保留当前目标、约束、最近关键交互和可复用工具结果；把旧对话按结构化摘要压缩，必要时从长期记忆或 RAG 回取。摘要必须带来源和版本，不能把模型猜测当事实写回。配合 token budget、缓存和不同模型路由，持续监控上下文占比与任务成功率。

## Q4：怎样防止上下文污染和 Prompt Injection？

**答：**明确指令层级，外部网页、文件和工具返回仅作为数据；在输入边界做检测与净化，在工具边界做权限控制和参数校验，在输出边界做敏感动作确认。对检索片段标注来源、信任级别和权限，模型即便被诱导也不能绕过服务端策略执行写操作。

## Q5：记忆冲突或过时信息怎么办？

**答：**长期记忆需要 `source`、`confidence`、`updated_at`、`expires_at`、`status` 与 supersedes 关系。检索时优先权威且新鲜的证据，出现冲突时展示不确定性、请求澄清或回到来源，而不是让模型投票。写入记忆需显式触发、去重和审核，避免把一次性对话误沉淀为长期事实。
