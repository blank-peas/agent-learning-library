# 02｜RAG 与知识增强

## Q1：讲一遍 RAG 的生产链路。

**答：**离线侧做解析、清洗去重、语义切分、补齐标题/权限/时间等元数据、向量化和索引构建；在线侧做鉴权与查询理解、召回、重排、上下文组装、带引用生成和结果校验。每个 chunk 都要保留来源、版本与权限，回答只引用调用者有权访问的证据。

## Q2：Chunk 大小和 overlap 怎样确定？

**答：**没有固定值，应由文档结构和评测决定。FAQ 可以更细，技术文档应按标题、段落或代码块等语义边界切分；overlap 只用于避免跨段信息断裂，不宜机械堆大。以标注 query 集比较 Recall@K、MRR、引用完整性和端到端正确性，选择在效果、延迟与成本间平衡的方案。

## Q3：向量召回不准，如何定位和改进？

**答：**先把问题拆成“正确文档没召回”还是“召回了但排序/生成没用好”。前者检查解析、切分、embedding、query 改写和 metadata filter；后者引入 BM25/向量等多路召回、RRF 融合和 cross-encoder rerank，并限制最终上下文噪声。每次改动按 query 类型分桶评估，避免平均分掩盖特定领域退化。

## Q4：RAG 与微调如何取舍？

**答：**知识需要及时更新、需要可追溯引用或无大量标注时选 RAG；模型需要学稳定的表达风格、分类规则或工具使用模式时考虑微调。常见组合是微调负责行为与格式，RAG 负责动态事实。不能用微调“记住”经常变化的知识，因为更新、回滚和溯源都很差。

## Q5：如何评估 RAG？

**答：**分层评估：检索看 Recall@K、MRR、NDCG；生成看正确性、相关性、groundedness/faithfulness 与引用覆盖；业务看任务完成率、拒答质量、时延和用户反馈。样本集要有正常、长尾、过期、冲突、无答案与权限边界样本，线上 bad case 回流后冻结为回归集。
