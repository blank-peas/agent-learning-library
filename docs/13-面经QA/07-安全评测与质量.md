# 07｜安全、评测与质量

## Q1：如何评估 Agent，而不是只评估最终回答？

**答：**按层拆分：意图和规划是否正确、检索证据是否相关、工具选择与参数是否合规、执行轨迹是否高效、最终答案是否正确且有依据。每层都有离线样本和指标，端到端再看任务完成率、时延、成本和人工接管率，这样才能定位改动为什么变好或变差。

## Q2：怎样构建评测集？

**答：**从真实任务与线上 bad case 抽样，覆盖正常、模糊、失败、越权、注入、长尾和边界条件；为每条定义可判定的目标、允许的证据或工具轨迹、评分规则。评测集版本化并冻结核心回归集，新增能力只能扩充样本，不能为了分数删掉失败题。

## Q3：LLM-as-Judge 能完全替代人工吗？

**答：**不能。它适合规模化比较和初筛，但可能有位置偏差、长度偏差、同模型偏好和领域知识误判。高风险或关键样本需人工标注；Judge 的 prompt、模型版本和一致性也要评估。对于工具调用和结构化结果，优先用规则、执行结果和断言评分。

## Q4：如何防 Prompt Injection？

**答：**把外部内容一律视为不可信数据，禁止它改变系统策略；最小权限与服务端授权是根本防线；对高危工具引入审批和 allowlist；输出使用 schema 校验与敏感数据过滤。还要把直接/间接注入样本放进回归集，定期红队测试而不是只依赖关键词拦截。

## Q5：上线后怎样持续提升质量？

**答：**建立闭环：trace 捕获失败 → 按模型、检索、工具、策略分类 → 复现为最小样本 → 修改并在冻结集回归 → 灰度发布和监控 → 将确认的 bad case 纳入正式评测集。成功率上升之外，还要监控成本、尾部时延、拒答率和安全事件，避免局部优化带来新的风险。
