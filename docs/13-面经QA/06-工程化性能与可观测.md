# 06｜工程化、性能与可观测

## Q1：为什么 Agent UI 不能只是聊天气泡？

**答：**Agent 是长任务和有副作用的任务系统。UI 应展示任务阶段、工具执行、引用、审批、失败原因与下一步，并支持取消、重试和恢复。对话文本只是呈现层，任务状态与消息状态应分离保存，避免断线后无法复原执行过程。

## Q2：SSE 和 WebSocket 如何选？

**答：**服务端单向流式输出、实现简单且需要穿透常规代理时优先 SSE；需要高频双向事件、协作编辑或客户端主动推送时用 WebSocket。无论选哪种，都要定义 event id、重连、顺序、幂等和最终状态查询接口，不能把网络连接当作任务可靠性的唯一依赖。

## Q3：Agent 系统怎样降低延迟和成本？

**答：**先按链路测量首 token、检索、工具和生成耗时；再使用缓存、并行无依赖调用、缩短有效上下文、轻量模型路由、预计算和流式输出。成本治理要按用户/任务/工具记录 token 与调用次数，并对异常长任务设置预算和降级，而不是只换一个更便宜模型。

## Q4：高并发时如何限流和降级？

**答：**入口按用户、租户与工具设配额，轻重请求分队列；任务 worker 无状态化并持久化状态以便水平扩容。超载时优先命中缓存或检索式回答，关闭昂贵的多 Agent/深度研究，排队或明确告知稍后完成。限流策略必须保护下游模型和业务系统，而非只保护前端。

## Q5：什么样的 Trace 才能排障？

**答：**一次请求贯穿 trace id，记录模型版本、prompt/上下文版本、检索文档 ID、工具名与脱敏参数、耗时、重试、审批、最终结果和错误分类。把 trace 与评测样本、线上 bad case、成本关联，才能判断问题在模型、检索、工具还是策略层。
